# Implementation Plan: WhimprFlow for iPhone (keyboard dictation)

## Context
WhimprFlow is a macOS/Windows Tauri dictation app (Rust core + React UI). SPEC.md marked mobile "SKIP". Koby now wants it on their **iPhone 14 Pro**, Wispr-Flow style: a **custom keyboard** with a mic button that dictates into any app. They're starting with a **free Apple ID** (upgrade to paid later if they like it), want **cloud cleanup first**, and want to **reuse the Rust core** from native Swift.

Constraints discovered:
- **No Xcode installed** (only Command Line Tools) and no signing identities → Phase 0 is setup.
- iPhone 14 Pro (A16, 16-core ANE) runs iOS 26/27 → **SpeechTranscriber/SpeechAnalyzer works** (on-device, no Apple Intelligence needed, no bundled model). **Foundation Models LLM does NOT** (needs 15 Pro+) → cleanup via cloud.
- iOS keyboards **cannot use the mic** → host app records while backgrounded (UIBackgroundModes `audio`, plist-only, works on a free team), Wispr "Flow Session" pattern.
- **Free team can't provision App Groups/shared Keychain** + builds expire every 7 days → keyboard↔app bridge must avoid App Groups (see Architecture).
- WhisperKey (github.com/grcamauer/WhisperKey) has **no license (all rights reserved)** → use as *design inspiration only*, copy no code. Ideas borrowed: ultra-light keyboard, host app owns audio/ML, session state, Darwin-notification signaling, XcodeGen `project.yml`.
- Rust core (`crates/whimpr-core`) is pure logic, no platform deps — portable to iOS as-is. `whimpr-asr` (whisper.cpp), `whimpr-audio` (cpal), `whimpr-llm-worker` (spawns a process), `whimpr-sidecar` are **not** used on iOS.

## Architecture Decisions
- **Native SwiftUI host app + UIKit keyboard extension**, in a new `ios/` dir, project generated by **XcodeGen** (`ios/project.yml`) so the project is text/diffable. Deployment target iOS 26.0.
- **ASR: Apple SpeechTranscriber** (iOS 26 SpeechAnalyzer) in the host app. Dictionary terms fed as `AnalysisContext` contextual strings. Fallback if it misbehaves in background: WhisperKit (MIT) small/base CoreML model.
- **Cleanup: cloud, Anthropic `claude-haiku-4-5` first** (Koby's existing key; OpenAI `gpt-4o-mini` optional later), HTTP via Swift `URLSession`; **prompt building, gates, post-processing come from Rust** (`whimpr-core::cleanup`). API key in iOS Keychain (host app only). Timeout/offline/gate-fail → raw transcript (same policy as desktop).
- **Rust reuse via UniFFI**: new crate `crates/whimpr-ffi` wrapping `whimpr-core` (cleanup `build_messages`/`post_process`/`gates::evaluate`/`pre_normalize_layout`, `DictionaryStore`, `StyleStore`, `StatsStore`, `Settings`). Built as `WhimprCore.xcframework` (aarch64-apple-ios + aarch64-apple-ios-sim) by `scripts/build-ios.sh`. Only the **host app** links Rust; keyboard stays tiny (memory limit).
- **Keyboard↔app bridge without App Groups** behind a `DictationBridge` protocol so a paid-account `AppGroupBridge` can drop in later:
  - Keyboard → app: open `whimprflow://flow` via responder-chain `openURL` (starts Flow Session); start/stop commands via **Darwin notifications** (`CFNotificationCenterGetDarwinNotifyCenter`, no entitlement).
  - App → keyboard: candidate A **loopback socket** (host app listens on 127.0.0.1 while session live; keyboard with Full Access connects) vs candidate B **UIPasteboard + Darwin "done"** (restore previous clipboard after insert). Spike picks one (prefer A: no clipboard clobbering).
  - User returns to the original app via the iOS "◀ Back" status-bar link (manual, accepted for v1).
- Persistence: Rust stores' JSON files in host app `Application Support/` (keyboard never reads them on free tier).

## Decision: recognizer (T7)
DictationTranscriber, not SpeechTranscriber (which the ASR bullet above originally named). Tested on the iPhone with a synthesized sentence: SpeechTranscriber ignored `AnalysisContext.contextualStrings` completely, while DictationTranscriber applied them ("Koby Welman… Zyphrex" instead of "Kobe Wellman… Zyxx") and still passed the general-accuracy test. The dictionary is the main way users fix names, so it wins.

## Decision: keyboard↔app transport (T4)
Loopback TCP socket (candidate A), not the pasteboard. It carries commands and results in both directions, with live partial text. A refused connection tells the keyboard there's no Flow session, so no Darwin notifications are needed. It doesn't touch the user's clipboard. It binds 127.0.0.1 only, and the app answers only the token the keyboard passed in `whimprflow://flow?token=…`. Needs the keyboard's Full Access (for networking), which dictation needed anyway.

## Risks and Mitigations
| Risk | Impact | Mitigation |
|---|---|---|
| SpeechTranscriber won't run while app backgrounded | High | T3 spike first; fallback WhisperKit on CPU/ANE |
| Loopback socket / pasteboard blocked for keyboard on free tier | High | T4 tries both; Full Access required; worst case copy-then-user-pastes |
| Responder-chain `openURL` from keyboard breaks on iOS 26/27 | Med | Fallback: user opens app manually/Shortcut to start session |
| iOS kills backgrounded host app (memory) | Med | Keep host app lean, no Rust heavy work idle; auto-restart prompt in keyboard |
| 7-day free-provisioning expiry | Low | Documented re-deploy step; paid upgrade later |
| Keyboard extension memory limit (~48–70MB) | Med | No Rust / no ML in keyboard |
